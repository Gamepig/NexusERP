# Bug 記錄 - 商品下拉選單跨公司資料洩漏

## 📅 基本資訊
- **發現日期**：2025-07-31
- **任務 ID**：2c (修復商品管理 - 商品下拉選單跨公司資料洩漏問題)
- **嚴重程度**：高 (嚴重安全問題 - 多租戶資料隔離失效)
- **狀態**：已解決
- **影響範圍**：所有使用商品下拉選單的功能，特別是銷售訂單建立頁面

## 🐛 問題描述
用戶在建立銷售訂單時，商品下拉選單顯示了其他公司的商品資料：
- **安全問題**：多租戶資料隔離機制失效
- **表現症狀**：下拉選單中出現如 "user0001_4972 的公司 商品 1" 等其他公司的商品
- **影響範圍**：所有需要選擇商品的功能頁面

## 🔄 重現步驟
1. 用戶登入系統（如 test@example.com）
2. 進入銷售訂單建立頁面：`http://127.0.0.1:8000/customers/1/orders/create`
3. 點擊商品下拉選單
4. 觀察到下拉選單顯示了其他公司的商品資料

## 🔍 根本原因分析

### 技術分析
1. **控制器問題**：
   - 位置：`app/Http/Controllers/API/ProductController.php:36-37`
   - 問題代碼：
     ```php
     // 允許存取所有產品（銷售訂單需要看到所有可用產品）
     // 原本的用戶篩選已移除，以便銷售人員能看到所有產品
     ```

2. **多租戶篩選機制被停用**：
   - 註釋說明：「允許存取所有產品」、「原本的用戶篩選已移除」
   - 影響：所有公司的商品資料都會被返回到前端
   - 安全風險：違反多租戶資料隔離原則

3. **業務邏輯誤解**：
   - 錯誤假設：銷售人員需要看到「所有產品」
   - 正確邏輯：銷售人員只應該看到「當前公司的產品」
   - Product 模型有 `company_id` 欄位，但未被正確使用

### 架構分析
- **多租戶模式**：系統採用 `company_id` 作為租戶隔離標識
- **會話管理**：`current_company_id` 儲存在用戶會話中
- **資料模型**：Product 模型包含 `company_id` 欄位用於多租戶隔離

## 🛠️ 解決方法

### 修復策略
重新啟用並正確實作多租戶篩選機制，使用 `company_id` 進行商品過濾

### 修復代碼

**修復前 (`app/Http/Controllers/API/ProductController.php:36-37`)：**
```php
// 允許存取所有產品（銷售訂單需要看到所有可用產品）
// 原本的用戶篩選已移除，以便銷售人員能看到所有產品
```

**修復後：**
```php
// 只顯示屬於當前公司的產品 - 多租戶篩選
$companyId = session('current_company_id') ?? session('app.current_company_id');
if ($companyId) {
    $query->where('company_id', $companyId);
}
```

### 修復要點
1. **啟用多租戶篩選**：移除錯誤的業務邏輯註釋
2. **使用正確的篩選條件**：使用 `company_id` 進行商品過濾
3. **會話變量處理**：支援兩種會話變量格式的回退機制
4. **安全性優先**：確保只返回當前公司的商品資料

## 🚫 預防措施

### 1. 業務邏輯驗證
- 銷售人員只能銷售自己公司的商品，不應看到其他公司商品
- 跨公司銷售需要專門的業務流程和權限控制
- 多租戶系統的基本原則：資料隔離是強制性的，不是可選的

### 2. 程式碼審查準則
- 禁止在生產環境中停用多租戶篩選機制
- 所有 API 控制器都必須實作適當的資料隔離
- 「允許存取所有資料」的註釋必須經過安全審查

### 3. 自動化測試
- 為所有涉及多租戶資料的 API 添加自動化測試
- 測試不同公司用戶之間的資料隔離
- 驗證 API 返回資料的公司歸屬

### 4. 安全檢查清單
- 檢查所有使用商品資料的 API 端點
- 驗證客戶、供應商等其他多租戶資料的篩選邏輯
- 建立定期的多租戶隔離檢查機制
